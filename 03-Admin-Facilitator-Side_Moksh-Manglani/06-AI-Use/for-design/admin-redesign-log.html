Admin Redesign Log
Admin panel · redesign log

From "this doesn't work" to a shipped decision

Six rounds of feedback on StudyBuddy's admin panel, what changed in response to each one, and the reasoning behind it — kept as a record for the project write-up and for anyone picking this up later.

Scope — Classes, Lessons, Overview, Settings, theming Entries — 6 Reviewer — Gill Dobbie (admin)

Every entry below follows the same shape: what was actually said, what was wrong with the page at the time, what got built in response, and why that specific change is a better answer than the alternatives. The feedback is lightly cleaned up for readability but not reworded in substance — where a comment was vague ("this looks off"), the problem section spells out what that turned out to mean once traced down.

Three things ran underneath most of these decisions, worth naming up front because they explain choices that might otherwise look arbitrary entry-by-entry.

Reference point
Canvas LMS course cards — the banner-image pattern most facilitators already recognise
Architecture
One token layer (colour, radius, shadow, type) driving every page, not per-page rebuilds
Decision method
Six full mock-ups built on real data before committing to a direction, not one guess
01

Classes and Lessons didn't do different jobs

Feedback
"For the admin Classes page — what I wanted to do is change that so each class comes up as a card, and you can click into it and see what lessons belong to it. That would allow us to more accurately navigate around the system. And the Lessons tab — right now it just has a table in it. I want it organised in a much better way."
Problem

Classes was a flat list — a name and some subject tags, no way to get from "Classes" to an actual lesson without leaving the page. Lessons was a single unsorted table showing the same information Classes already had, with no search, no filter, and no grouping by grade or subject.

Change

Classes became a three-level structure: class cards, then subject cards inside a class, then a lesson list scoped to that subject — each level with a breadcrumb and a "Create lesson" shortcut pre-filled for that subject. Lessons stayed a separate, org-wide index: sectioned by Class · Subject, collapsible, with a search box and a status filter.

Why it's better

The two pages now do different jobs instead of one quietly duplicating the other. Classes mirrors the real data model — a class contains subjects, a subject contains lessons — so navigating it matches how an admin already thinks about their curriculum. Lessons is the "find anything fast" surface, which only starts to matter once there are more lessons than fit on one screen.

02

No account controls, and a dashboard with nothing on it

Feedback
"Maybe a settings page for — let's say — this Gill Dobbie, which I'm logged in as. So if I click there, there's a settings page which would allow me to change things."
Problem

There was no account page anywhere in the app — "Sign out" was the only control an admin had over their own account. Overview, the first screen after logging in, showed two numbers and a single link.

Change

A real Settings page: change display name, change password (with the current password verified before it's accepted), change the organisation's name. Overview grew five stat tiles, three quick-links, and a recently-updated lessons list.

Why it's better

An admin can manage their own account without a developer doing it for them. Overview now answers "what needs my attention" on sight, instead of making that a click into Lessons to find out.

03

Picking a direction by looking, not guessing

Feedback
"I like the minimalistic design we have going on, so I want to stay on theme with that — but maybe add one or two variants which are completely different, so we can identify which one suits the users best." Then, after seeing three options: "make it a total of six completely different design styles — different libraries, different components — to give me a sense of what's possible."
Problem

Proposing a single redesign and asking "do you like it" isn't really a design decision — it's a guess dressed up as one, with nothing to compare it against.

Change

Built a single comparison page rendering the same real data — Gill Dobbie's actual lesson counts, the actual four grades — across six distinct systems: a dark developer-console style, a formal enterprise style, a soft "productivity tool" style, Material Design 3, a schoolbook/notebook style built specifically around the K-12 subject matter, and a polished version of the existing palette.

Why it's better

Comparing six fully worked examples side by side, on real data instead of lorem ipsum, turns "what should this look like" into something you can actually see and decide on quickly — rather than something you have to picture from a written description.

04

Committing: three themes, no more emoji, real course cards

Feedback
"I really like the Refined Current, the Studio — but with class cards similar to the Atlas one — and the Ledger one, though refine this one more. I'm not a big fan of those emojis, so let's take those out and replace them with good images. And I want the class cards to look like the Canvas cards, with the image banner."
Problem

Emoji render differently across operating systems and browsers, can't be recoloured or resized to match a design system, and read as informal for a platform whose entire premise is giving unqualified facilitators something structured and dependable. Class cards had no visual identity past a name and a count.

Change

A real, switchable theme system: one set of colour/radius/shadow/type tokens per style, driving the same shared components — no page needs its own copy of anything. Sidebar and dashboard emoji replaced with lucide icons (the same set shadcn/ui ships with by default). Class cards rebuilt Canvas-style — a banner on top, title and counts below — with generated art as the always-on default so a class never looks unfinished, and a real upload option layered on top of that.

Why it's better

Because the look lives in tokens, not per-page styling, trying a different theme costs nothing structurally — flip one attribute and the whole admin panel repaints. Icons now read consistently and recolour correctly per theme. Canvas is the LMS most people have actually used, so classes now look the way a course catalogue is expected to look — closing exactly the gap the flat list left.

05

Controls you set once shouldn't sit in the way forever

Feedback
"I kind of want those toggles to be in the settings cog. When you click that settings icon, it shows you those two toggles in a dropdown — and it also has a third option, to go to advanced settings."
Problem

The nav-layout and theme switches lived as two permanently visible controls in the top-right of every page — competing with actual page content for attention on every single screen, for a decision an admin makes once and rarely touches again.

Change

Both switches collapsed behind one settings-gear icon. Clicking it opens a dropdown with the two toggles stacked, plus an "Advanced settings" link through to the real account settings page.

Why it's better

Controls used constantly should stay visible; controls set once and forgotten shouldn't. One familiar icon — the same pattern Linear, Notion, and GitHub all use for display preferences — keeps the page quiet by default without making the options any harder to reach.

06

Diligence: chasing down a layout bug that turned out to be two

Feedback
"Why is the full space not being utilised? The other pages look great." — then, after a first fix shipped: "this looks off, need to fix this."
Problem

Two separate bugs, stacked. First, Classes and its subject pages still carried a width limit left over from before the card-grid redesign — meant to keep a single "add a class" form narrow, it was quietly capping the entire page, cards included. Fixing that exposed a second, subtler bug: with the sidebar layout active, the main content area sits inside a CSS Grid cell, and a Grid item's default width is "shrink to fit its content," not "stretch to fill the column" — so the centering rule had no spare room to distribute, because there wasn't any.

Change

Moved the width limit off the page and onto just the add-class form. Forced the main content area to actually claim its column's full width before capping and centering it.

Why it's better

Small fixes, but they're the difference between a page that looks unfinished on a wide monitor and one that doesn't. Worth keeping on record because the second bug is a genuine, easy-to-repeat CSS Grid behaviour — not a typo, and not obvious from the symptom alone.
