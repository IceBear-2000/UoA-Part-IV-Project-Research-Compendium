2. What StudyBuddy Actually Does

The problem it solves: running structured K-12 lessons normally requires a trained facilitator who can plan and adapt content. StudyBuddy inverts this — an admin/coordinator builds a lesson once as a sequence of typed "blocks" (video, workbook, activity, worksheet, reading, quiz, discussion, break, note), and any facilitator — qualified or not — can deliver that exact lesson by following the platform's own guided flow, step by step, with facilitator notes at each stage.

Two roles, strictly separated (enforced server-side, not just hidden in the UI):

  • Admin / Coordinator — creates and publishes lessons, builds the block-by-block flow (drag-and-drop reordering), manages the class → subject hierarchy, assigns facilitators to specific classes/subjects, reviews and approves new facilitator applications, messages facilitators, and has an AI worksheet generator (currently mocked).
  • Facilitator — sees only the classes/subjects they've been explicitly assigned, browses only published lessons within those, and plays through a lesson via a strict flow player: blocks are locked until you reach them in order, then once the lesson is fully completed, every block becomes freely navigable (so a facilitator can revisit any step afterwards without being able to skip ahead the first time through).

Content hierarchy: Organisation → Class (a.k.a. "Grade") → Subject → Lesson → Block

3. Technology Stack & Why

Choice Reasoning
Next.js 14, App Router Server Components for data-heavy admin/facilitator views, Server Actions for all mutations (no separate REST/API layer needed), middleware for route-level auth gating.
Supabase Postgres (via Prisma) + Auth (email/password, magic-link-style invite flow) + Storage (private buckets with signed URLs for uploaded lesson resources) — one vendor for three infrastructure needs.
Prisma ORM, pinned to ^6.19.3 Prisma v7 removed the inline datasource.url syntax the project's schema was originally written with. Rather than rewrite the schema (the project's own standing rule was "never deviate from schema.prisma without asking first"), the dependency was pinned instead.
Tailwind CSS + a bespoke design-token system The project ships with a DESIGN_TOKENS.md defining an exact colour palette (a warm "claymorphism"/soft-paper aesthetic: clay, sage, blue, gold, rose, each with a -soft tinted variant), spacing, radii, and shadow values. These were wired into tailwind.config.ts as first-class theme colours (bg-clay, bg-sage-soft, etc.) in the very first session, and every feature built since — including features added months after the original plan — has matched this palette exactly, rather than drifting into ad-hoc styling.
Resend Chosen over a fully-mocked email flow specifically so the facilitator-invite emails would be real, testable deliverability — not just a console.log. Built with a graceful no-op fallback (shows the invite link directly in the admin UI) so the whole approval flow was testable before a Resend account/API key existed.
Vercel Standard zero-config deploy target for Next.js; the project's own build sequence explicitly recommended deploying early rather than waiting.

4. What Has Been Built — By Phase

The project was built against a 9-session sequence (CLAUDE_CODE_SEQUENCE.md), and then extended well beyond it as the user's needs became clearer. Both parts matter for a report: the first shows disciplined, planned execution; the second shows the project responding to real requirements as they emerged — which is exactly what a real engineering project looks like.

4.1 The original 9-session plan (all complete)

  1. Scaffold — Next.js + TypeScript + Tailwind project, Prisma wired to Supabase, design tokens loaded as Tailwind theme values, confirmed the dev server and Tailwind rendering worked before writing any real features.
  2. Database — ran the initial migration, wrote a seed script creating one organisation, one admin, two facilitators, two classes ("Grade 1", "Grade 2"), several subjects, and one fully-built 5-block lesson ("Counting to 20") matching the original design mockup.
  3. Auth & roles — Supabase Auth (email/password), with every signed-in user mirrored into a local User table (keyed by Supabase's authId) so role information is queryable without extra network calls. Middleware enforces that admin routes are unreachable by facilitators and vice versa — at the request level, not just hidden nav links.
  4. Admin: lesson CRUD — lessons list, creation form (name/class/subject required; duration, description, learning objectives optional and marked "Recommended" per the product brief), Draft/Published status toggle.
  5. Admin: block builder — the core lesson-authoring tool. Add-block type picker (9 types), drag-and-drop reordering (@dnd-kit), type-specific content editors (Video gets a URL + duration field, Workbook gets a page range, Activity gets instructions, Worksheet gets a file-or-link), and a generic instructions field for the remaining types (Reading/Quiz/Discussion/Break/Note). File upload (PDF/Word/PowerPoint) was added on top of this for Reading and Worksheet blocks specifically, backed by a private Supabase Storage bucket and signed URLs — deliberately not offered on Video blocks, which already have their own URL field.
  6. Facilitator: browse — read-only dashboard → assigned classes → subjects → lessons. Strictly scoped by the FacilitatorAssignment join table and filtered to Published lessons only.
  7. The lesson flow player — the most critical piece of the whole system. Built against real LessonProgress rows (one per facilitator per lesson, reused on resume rather than duplicated). State — done / active / locked / free-navigation — is derived from currentBlockIndex, completedBlockIds, and completedAt. Marking a block done is enforced server-side: a locked block can't be fetched or completed no matter what the client sends. Once completedAt is set, every block unlocks for free navigation. This was tested by literally starting a lesson, completing 2 of 5 blocks, refreshing the page, and confirming the facilitator resumed at block 3 with 1–2 still marked done — then completing the rest and confirming free click-back-to-block-1 behaviour.
  8. Admin: facilitator management & assignment — a facilitator list (table and card view), and an Assign modal that writes to FacilitatorAssignment. Reachable from two different places in the UI (the facilitator's own profile, and later, directly from class/subject context) but both write to the exact same underlying table — a deliberate decision to avoid two competing data models for the same relationship.
  9. Messaging, notifications, worksheet generator (mock) — see §4.3 below; this was completed as part of the most recent working session.

4.2 The authorization / onboarding system (built beyond the original plan)

Partway through the project, the user asked for a proper request-based onboarding flow instead of open self-registration. Four design decisions were made explicitly with the user before building (each was proposed as a structured choice and confirmed):

  1. "Request first, invite later." The public signup form collects only a name and email — no password. This creates a SignupRequest row (status PENDING). No Supabase Auth account and no User row exist yet.
  2. Real email, not a mock, via Resend — with a graceful no-op fallback (the generated invite link is shown directly in the admin UI instead of emailed) whenever RESEND_API_KEY isn't configured, so the entire flow stays testable without depending on email infrastructure.
  3. One combined approval step. The admin picks which class(es)/subject(s) to grant in the same action as approving the request — not as a separate follow-up step. The approval modal lets the admin stage multiple class/subject grants before submitting once.
  4. An optional "which class are you hoping to help with?" free-text field on the request form — informational only; the admin can grant anything regardless of what was requested.

The resulting flow: anonymous request → shows up on an admin "Requests" dashboard with a live unread-style badge count → admin approves with one or more class/subject grants staged → this simultaneously creates the real (unconfirmed) Supabase Auth account, the local User row, the FacilitatorAssignment rows, and generates a one-time invite link → Resend emails that link (or the admin sees it directly in the UI as a copy-paste fallback) → the recipient clicks it, sets a password, and lands as an active facilitator with exactly the access they were granted.

New schema for this: a SignupRequestStatus enum (PENDING / APPROVED / REJECTED) and a SignupRequest model tracking who reviewed it, when, and (for approvals) which User it ultimately created.

4.3 Messaging, notifications, and the worksheet generator (most recently completed session)

  • Messaging — simple 1:1 chat, strictly admin ↔ facilitator (never facilitator-to-facilitator or admin-to-admin — enforced server-side, not just by UI). Admins see a list of all their facilitators and can open a thread with each; facilitators see a single "Chat with admin" view. A shared MessagingThread component drives both, so the two role-specific pages differ only in who they fetch as conversation partners, not in how the chat itself renders.
  • In-app notifications — a new Notification model, deliberately kept simple (one flat list per user, "mark all read" on opening the inbox — no per-row read tracking needed for that page). The one piece of extra design: notifications carry an optional fromUserId, set only for message-type notifications, so opening one conversation thread clears only that thread's unread badge — not unrelated unread messages from someone else. Triggered by: a new message, being approved with class access, or being granted a new assignment via the standalone "Assign" flow.
  • Worksheet generator (mock) — a form (topic, class/grade, subject, number of questions, optional style notes) that, after a short simulated delay, renders a plausible-looking worksheet preview with numbered questions and answer lines, plus Regenerate and Copy-as-text actions. Deliberately built so the entire "generate" step lives in one isolated function (lib/worksheet-generator.ts) with a clean input/output contract — swapping the mock body for a real LLM call later requires touching that one function only, not any of its callers.

4.4 Admin Classes & Subjects management (built after the above, most recent feature)

Originally, classes and subjects only existed via the seed script — there was no way to add a new class or subject from the UI. Added a /admin/classes page: an inline "add class" form, and a per-class "+ Add subject" control that reveals a small inline input. Both include case-insensitive duplicate-name guards (so "grade 1" is correctly rejected as a duplicate of "Grade 1"). New classes/subjects are immediately available everywhere else in the app that reads them — confirmed live by creating a test "Grade 3" class with a "Reading" subject and watching it appear correctly in the lesson-creation dropdown without any extra wiring.

4.5 Other fixes worth mentioning

  • Video block playback bug. Admins could paste a YouTube link into a Video block, but the facilitator-side player used a bare HTML5 <video src="…"> tag — which can only play direct video files, not a YouTube page URL (which returns an HTML page, not a raw video stream, when requested that way). Fixed with a small resolveVideoEmbed() helper that detects YouTube/Vimeo links and converts them into proper <iframe> embeds, falling back to a real <video> tag only for genuine direct file links. A hint was also added under the admin's "Video URL" field clarifying what's supported, since nothing previously told the admin what kind of link was expected.

5. Design Decisions Worth Highlighting in a Report

These are the decisions with real engineering reasoning behind them, not arbitrary choices — good material for a "design and rationale" section:

  • Server-side-only enforcement of the lesson-flow lock state. The client is never trusted to say "this block is unlocked" — every mutation re-derives lock state from the database. This was a deliberate integrity decision for the most important piece of the app (the flow player), not an afterthought.
  • Block content as flexible JSON, not per-type tables. A Block row has one content: Json column whose shape depends on type (documented directly in the Prisma schema comments). This avoids nine separate content tables for nine block types, at the cost of weaker compile-time type safety — a trade-off made consciously and documented in code (including explicit eslint-disable comments explaining why any is used there, rather than silently suppressing the warning).
  • "Request first, invite later" over open self-registration. A security/control decision — nobody can create their own facilitator account unilaterally; every account traces back to an admin's explicit approval.
  • Isolated, swappable "generate" functions. Both the worksheet generator and (implicitly) the video-embed resolver were built as single, narrow functions with a clean contract, specifically so the "real" version (an LLM call; broader embed-provider support) can replace the body later without touching any caller.
  • One data model for facilitator assignment, reached from two UI entry points. Rather than build "assign from the facilitator page" and "assign from the class page" as two different features, both write to the same FacilitatorAssignment table through the same server action.
  • Design-token fidelity across the entire build, not just the initially-scoped screens. Every feature added after the original 9-session plan — messaging, notifications, the worksheet generator, class management — was still built to match DESIGN_TOKENS.md exactly (same colour tokens, same card/pill/badge visual language), rather than drifting into ad-hoc styling as the project grew organically.

6. Engineering Challenges & How They Were Diagnosed — the "innovation" narrative

This section is the strongest material for a report, because each of these is a case of "the code looked correct, dev-mode testing passed, and it was still wrong" — caught only through deliberately rigorous, live verification rather than trusting green checkmarks.

6.1 The PKCE-vs-implicit-flow bug (the single biggest one)

What happened: the invite-link architecture was originally built assuming Supabase's invite emails would redirect back to the app with a ?code=xxx query parameter (the standard PKCE OAuth pattern), to be exchanged for a session inside a Next.js Route Handler.

How it was caught: rather than trust this design, the actual generated invite link was captured and inspected directly — first by trying to click it in-browser, then, when that was blocked by sandboxing, by mirroring the exact request with curl to see the real HTTP redirect Supabase issued. The real redirect carried #access_token=…&refresh_token=… in the URL fragment, not the query string.

Why this matters: browsers never send the URL fragment to the server — it's client-side only. A Route Handler literally cannot read it, under any circumstances. The root cause: Supabase's PKCE flow requires a code_verifier that only exists if a browser client itself initiated the sign-in — but an admin-generated invite link has no browser involved at generation time, so Supabase silently falls back to the older "implicit" flow (tokens directly in the fragment) instead.

The fix: the Route Handler was replaced with a Client Component that reads window.location.hash directly and calls Supabase's client-side setSession(), letting the browser-side Supabase client persist the session as cookies for subsequent server-rendered pages to read. Without this fix, every single real invite link would have silently failed — a bug that dev-mode testing with fake data would never have caught, because it only manifests when a real link is actually clicked.

6.2 A UI bug that would have hidden the invite link entirely

The admin approval modal was designed to show a success screen with the invite link (for the no-Resend-key fallback case). But the underlying list component had its "no pending requests" empty state gated before the modal's own render — so the instant the approved request dropped out of the pending list (which happens immediately, via the same page refresh that shows the approval succeeded), the modal unmounted before the admin ever saw the link. Fixed by decoupling the modal's render from that empty-state branch. Caught only by watching the actual UI after a real approval, not by reading the code.

6.3 A session-drop bug in the messaging feature

The message-send button initially used a <form> whose action was a local function that itself called a bound Server Action. Under this specific composition (rather than a plain click handler calling the Server Action directly — the pattern already proven reliable elsewhere in the app), sending a message would occasionally and then consistently bounce the user back to the login page mid-send. Diagnosed by comparing against the working pattern already used successfully elsewhere in the codebase (a plain onClick handler with local component state) and rewriting the composer to match it — which fixed it completely. A related contributing factor was also found and fixed: React 18's Strict Mode deliberately double-invokes effects in development, so the "mark this conversation read" effect was firing twice in quick succession; a ref-guard was added so it only fires once per thread, since two near-simultaneous mutating requests were a plausible trigger for Supabase's session-refresh logic to misbehave.

6.4 Smaller but real issues found along the way

  • A missing double-submit guard caused two duplicate lessons to be created in real usage from a single button click that wasn't disabled while its request was in flight. Fixed with useFormStatus, then generalized into one shared SubmitButton component reused across the whole app instead of re-solving it per form.
  • A real, pre-existing security gap: an audit found that none of the existing admin Server Actions actually verified the caller's role server-side — protection existed only via hiding admin nav links in the UI, meaning a facilitator who knew (or guessed) an admin endpoint URL could have called it directly. Fixed by adding a requireAdmin() check retrofitted onto every admin action, not just new ones going forward.
  • The production build caught errors the dev server never showed. Running next build (as required before any real deploy) enforces ESLint rules that next dev doesn't block on. Several pre-existing any-typed values and unused variables across multiple files only surfaced at this point — a good reminder that "works in dev" and "builds for production" are genuinely different bars.
  • Infrastructure quirks specific to the dev environment, documented for completeness rather than treated as code bugs: an IPv6-only direct Postgres connection failing in this sandbox (fixed by switching to Supabase's Session Pooler connection string), and Supabase's connection pool (capped at 17 connections on this project's tier) occasionally being exhausted under unusually rapid automated testing — resolved by restarting the dev server, not by changing application code.

  5. ⚠️ Gap: the admin Classes/Subjects management feature (§4.4) was built after that push, and has not been committed or pushed since. As of this document, git log shows exactly one commit. If the live Vercel deployment was connected to this repo, it currently does not include Classes/Subjects management.
  6. Vercel connection itself was handed off as instructions, not completed by the assistant — creating/logging into a Vercel account and connecting it to the GitHub repo requires the user's own authentication, which is outside what an AI assistant can or should do on someone's behalf. Practical takeaway for whoever picks this up next: before treating the app as "deployed," confirm (a) whether a Vercel project actually exists and is connected to this GitHub repo, (b) what URL it's live at, and (c) that the newer Classes/Subjects commit has actually been pushed and redeployed. None of these should be assumed from this document alone.
